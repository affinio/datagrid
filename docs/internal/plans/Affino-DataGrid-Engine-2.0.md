# Affino DataGrid Engine 2.0

Полный план архитектуры, контрактов и поэтапной реализации

Редакция: 18 октября 2026 года. Статус: предлагаемая целевая спецификация для обсуждения и реализации.

Документ заменяет исходную концепцию Engine 2.0. Он описывает, как строить систему, но не утверждает, что перечисленные проблемы обнаружены в текущем исходном коде Affino. Перед изменениями необходим короткий аудит существующей реализации. Примеры TypeScript показывают проектируемые контракты; это не готовая библиотека и не утверждённый окончательный API.

## 1. Цель и границы Engine 2.0

Affino должен стать библиотекой DataGrid с независимым от UI-фреймворка ядром, однозначными владельцами состояния, атомарными локальными изменениями и согласованными публикациями представления.

Качество архитектуры определяется поведением: редактирование, сортировка, выбор, виртуализация и серверные обновления должны работать совместно без потери данных, скачков фокуса, устаревших ответов и скрытой частичной обработки.

Engine 2.0 должен поддерживать:

- небольшой локальный grid с дешёвым путём исполнения;
- большие локальные наборы с виртуализацией и пакетными обновлениями;
- удалённые наборы, которые никогда не загружаются полностью;
- независимые Vue- и React-адаптеры;
- расширяемые вычисления, grouping, aggregation и pivot;
- тестирование семантики без браузера и проверку реальных взаимодействий в браузере.

Начальная реализация не обязана включать все эти возможности. Однако публичные контракты не должны предполагать, что все данные всегда локальны, любые операции синхронны или любая строка представляет исходную запись.

На первом этапе не требуются Canvas, WASM, универсальный оптимизатор запросов, распределённые транзакции, collaborative editing или event sourcing. Они не являются условиями качественного Engine 2.0.

## 2. Базовые инварианты

Следующие правила обязательны и должны иметь проверку там, где впервые реализуется соответствующая возможность.

| Инвариант | Практическое следствие |
| --- | --- |
| У каждой части изменяемого состояния один определённый владелец | Engine и приложение не записывают одновременно в одну независимую копию selection или sorting |
| Опубликованное представление согласовано | Renderer не соединяет новые данные со старой несовместимой геометрией или projection |
| Локальная атомарная операция видна целиком | Paste не оставляет половину записанных ячеек после ошибки validation |
| Идентичность не равна позиции | Индекс строки после сортировки не используется как ID записи |
| Асинхронный результат проверяется перед применением | Отмена запроса — оптимизация; проверка актуальности результата — требование корректности |
| Полнота набора данных известна | Сортировка загруженного блока не выдаётся за сортировку всего удалённого набора |
| Публичные snapshots неизменяемы | Старый snapshot не меняется после следующего commit |
| UI-адаптер не повторяет бизнес-правила | Eligibility, selection transitions и commit/cancel редактирования общие для всех адаптеров |
| Ошибка пользовательского расширения не повреждает состояние | Вычисления расширения завершаются до атомарного swap либо дают контролируемую ошибку |
| Ресурсы имеют владельца и срок жизни | У подписок, запросов, worker-задач и кэшей есть dispose, cancellation или eviction |
| Оптимизация сохраняет семантику | Incremental path даёт тот же результат, что эталонный полный пересчёт |
| Публикация и отображение различаются | Готовность snapshot не означает, что браузер уже нарисовал кадр |

Детерминированность означает одинаковый результат при одинаковом исходном состоянии, конфигурации и последовательности всех входов: команд, source updates, ответов внешних операций и явно переданных значений времени/случайности. Одной записи пользовательских команд для полного replay асинхронной системы недостаточно.

## 3. Архитектурные границы

| Подсистема | Владеет | Не должна делать |
| --- | --- | --- |
| Public API | Типизированными командами, чтением snapshots, подписками, lifecycle | Выдавать изменяемые внутренние структуры |
| Engine coordinator | Порядком операций, проверкой предусловий, локальными commits, публикациями | Становиться хранилищем всех алгоритмов и DOM-событий |
| State ownership | Режимами владения, принятием внешнего состояния, ревизиями | Создавать два источника истины для одного slice |
| Data access | Query sessions, диапазонами/курсорами, кэшем, source events | Подменять глобальную обработку локальной без корректной семантики |
| Projection и compute | Производными значениями, фильтрацией, сортировкой, группировкой, агрегацией | Управлять DOM или focus() |
| Interaction semantics | Selection, editing, eligibility, переходами жестов | Принимать MouseEvent как доменный контракт |
| Geometry и viewport | Координатами, окнами, измерениями, scroll anchoring | Читать DOM напрямую |
| Publication | Совместимыми версиями и неизменяемыми snapshot handles | Публиковать частично собранный результат |
| Framework adapter | Подписками фреймворка, lifecycle, преобразованием событий | Повторно сортировать данные или решать, допустим ли paste |
| DOM renderer/platform | Элементами, измерениями, focus, clipboard API, ARIA-атрибутами | Хранить независимую бизнес-модель grid |

Зависимости направлены от адаптеров к публичным контрактам core. Core не импортирует Vue, React, DOM-типы или браузерные глобальные объекты. Платформенные возможности передаются через порты.

Общие DOM-механизмы можно вынести в внутренний модуль, используемый обоими адаптерами. Отдельный npm-пакет оправдан только самостоятельным переиспользованием и сопровождением.

## 4. Владение состоянием

### 4.1. Четыре категории

| Категория | Примеры | Правило |
| --- | --- | --- |
| Authoritative state | Подтверждённые значения записей, схема, принятый запрос | Имеет конкретного владельца: engine, приложение или source |
| Derived state | Отфильтрованные ID, порядок строк, агрегаты, вычисляемые поля | Вычисляется из объявленных входов; не является вторым authoritative state |
| Transient state | Черновик редактора, resize preview, drag preview, hover | Живёт ограниченное время; не обязано попадать в Undo |
| Published presentation | Готовая projection, окно, layout, selection, logical focus | Только чтение; помечено совместимыми версиями |

Projection не следует одновременно хранить как независимо редактируемую часть View State и как результат pipeline. Изменяемы параметры запроса; projection — их производное представление.

### 4.2. Режимы ownership

Для каждого поддерживаемого slice выбирается режим при создании grid:

1. **Internal:** engine хранит и меняет slice.
2. **Controlled:** приложение хранит slice; engine выдаёт предложение изменения с request ID и базовой версией. Подтверждённый вход приложения проходит через общий ingest-путь.
3. **Source-authoritative data:** сервер или внешний store владеет подтверждёнными данными; engine хранит кэш, черновики и, при включении, optimistic overlay.

Optimistic overlay не считается подтверждённым источником истины. Он содержит mutation ID, базовую версию и статус ожидания.

Контракт controlled-режима определяет: принятие, отказ, замену предложения более новым значением, отмену и порядок приходящих ответов. Нельзя вызывать onChange и тут же считать внешнее состояние подтверждённым.

Команда, требующая атомарного изменения нескольких slices с разными владельцами, разрешается только при наличии общего host transaction contract. Иначе команда отклоняется как неподдерживаемая в выбранном режиме либо заранее документируется как многошаговый процесс без общей атомарности. Engine не может обещать атомарность чужого store.

На старте поддержать internal-режим и ограниченный набор controlled slices, например sorting/filtering/selection. Динамическая смена владельца slice после создания grid не поддерживается без отдельного протокола передачи владения.

## 5. Идентичность, типы и модель значений

### 5.1. Разные пространства идентичности

Нужны как минимум RowId, ColumnId, NodeId, QueryKey, SourceEpoch, CommitId и PublicationId. В TypeScript желательно номинально различать их через branded types.

- RowId идентифицирует исходную запись в пределах source identity/epoch.
- ColumnId стабилен при перестановке, скрытии и pinning.
- NodeId идентифицирует узел projection: запись, группу, subtotal или placeholder.
- Индексы являются координатами конкретной projection и не переживают её смену автоматически.

Групповой NodeId строится из спецификации группировки и канонически кодированного пути ключей. Простая конкатенация через разделитель недопустима из-за коллизий. Pivot-колонки получают ID из спецификации pivot, пути ключей и measure ID. Placeholder не получает фиктивный RowId: после загрузки происходит явная замена узла.

Удалённая запись с повторно использованным внешним ID должна отличаться incarnation/version либо новым SourceEpoch. Это важно для Undo и поздних ответов.

### 5.2. Значения

```ts
type CellValue<T> =
  | { kind: 'value'; value: T }
  | { kind: 'null' }
  | { kind: 'missing' }
  | { kind: 'loading' }
  | { kind: 'error'; code: string; message?: string };
```

Различать raw value, computed value, formatted text и editor draft. Сортировка и агрегация работают с типизированными значениями, а не с formatted text. Правила обработки null/missing/errors определены для каждой операции.

Column schema задаёт accessor, parser, validation, comparator, formatter и при необходимости aggregator. Не все функции обязательны, но их defaults должны быть документированы. Валюта, decimal, даты и timezone не получают неявную общую семантику JavaScript number/string.

UI-компонент ячейки принадлежит адаптеру и связывается с ColumnId или renderer key. Core не хранит VNode, ReactElement и DOM-узлы.

Потребитель не может незаметно мутировать исходные строки, на которые опирается engine. Для object-row режима требуется контракт неизменяемых входов и явных patches/replacements; альтернативный store обеспечивает versioned reads. Простого readonly в TypeScript для runtime-гарантии недостаточно. Политика копирования и защитных проверок задаётся явно.

## 6. Команды, подготовка и локальные транзакции

### 6.1. Три вида входов

- **Domain commands:** edit, paste, delete, sort.set, group.set, selection.set.
- **Interaction updates:** pointer position, resize preview, drag preview, scroll observations.
- **External inputs:** source patches, acknowledgements, query results, measurements.

Все входы проходят проверки совместимости, но не обязаны создавать одинаковый журнал или иметь одинаковую стоимость. Pointer movement не становится отдельным пунктом Undo.

### 6.2. Жизненный цикл команды

1. Нормализовать команду и проверить наличие capability.
2. Проверить eligibility и разрешения приложения. Серверная авторизация всё равно выполняется сервером.
3. Зафиксировать логические цели и read set: какие значения/версии влияют на результат.
4. Подготовить план изменений. Запустить нужные parsing/validation без изменения authoritative state.
5. Перед commit повторно проверить предусловия.
6. Построить следующий локальный state и ChangeSet.
7. Одним коротким синхронным swap зафиксировать локальную транзакцию и назначить CommitId.
8. Инвалидировать зависимые вычисления, запланировать публикацию и необходимые внешние effects.

Асинхронную validation нельзя выполнять внутри открытой локальной транзакции. Она относится к подготовке. Если за время ожидания read set изменился, результат отвергается или подготовка повторяется по явной политике.

Проверка конфликтов не должна зависеть от любого изменения глобального счётчика: scroll не делает редактирование устаревшим. Используются релевантные row/cell/schema/query versions.

Callbacks и плагины не вызываются в критической секции атомарного swap. Ошибка обработчика уведомления не отменяет уже завершённый commit; она изолируется и диагностируется. Команда, вызванная из уведомления, ставится в очередь следующей операции, исключая reentrant mutation.

### 6.3. Что возвращает API

Один boolean ok недостаточен. Предлагаемый смысловой контракт:

```ts
type CommandReceipt =
  | { status: 'rejected'; error: GridError }
  | { status: 'committed'; operation: OperationHandle }
  | { status: 'pending'; operation: OperationHandle };

interface OperationHandle {
  readonly id: OperationId;
  committed: Promise<CommitOutcome>;
  published: Promise<PublicationOutcome>;
  confirmed: Promise<ConfirmationOutcome>;
  cancel(): CancelOutcome;
}
```

Имена GridError и outcome-типов здесь обозначают отдельные discriminated unions, которые фиксируются в ADR перед кодированием.

- committed сообщает о локальной фиксации или терминальном отказе/отмене.
- published сообщает о совместимой публикации, включающей результат, либо об explicit superseded/failed/disposed outcome.
- confirmed сообщает о подтверждении authoritative owner, конфликте, отказе, неизвестном результате записи или not-applicable для локальной операции.
- Отмена до commit предотвращает фиксацию, если она ещё возможна. После commit cancel не означает rollback. Нужна отдельная компенсирующая команда.
- Ни один handle не остаётся навсегда ожидающим из-за dispose, supersession или ошибки вычисления.

PublicationOutcome не равен браузерному paint. При необходимости UI-адаптер предоставляет отдельный presentation acknowledgement для метрик и focus lifecycle.

### 6.4. ChangeSet

ChangeSet описывает затронутые RowId, ColumnId, вставки, удаления, старые/новые версии и структурные изменения. Он является входом invalidation, а не универсальной копией всех данных.

Для небольшого patch допустим точный список ячеек. Для больших импортов используются компактные диапазоны, block references или full-invalidation marker. Нельзя создавать миллионы мелких объектов только ради описания массовой замены.

### 6.5. Область атомарности

Вместо неоднозначного atomic: true использовать atomicity: 'local' | 'source' | 'none'. Local гарантирует атомарное применение в локальном engine, но не серверную запись. Source требует атомарной записи authoritative source и соответствующего capability; неподдерживаемая гарантия отклоняется до отправки изменений. None допускает документированный поэлементный результат. В source-режиме optimistic UI, если включён, остаётся предварительным и не объявляется серверным подтверждением.

## 7. Согласованная публикация и revisions

### 7.1. Разделить версии

| Идентификатор | Назначение |
| --- | --- |
| SourceEpoch | Замена источника или сброс несовместимого состояния |
| OwnerVersion | Версия подтверждённых данных внешнего владельца |
| CommitId | Порядок принятых локальных изменений |
| QueryKey / QueryGeneration | Семантика запроса и конкретный цикл его выполнения |
| ProjectionRevision | Версия материализованного порядка и состава узлов |
| LayoutRevision | Версия размеров и геометрии |
| InteractionRevision | Версия selection, logical focus и других согласуемых взаимодействий |
| PublicationId | Конкретная совместимая публикация |

Версии подсистем предназначены для dependency tracking и отбрасывания устаревших результатов. Один глобальный счётчик остаётся полезен для порядка commits/publications, но не заменяет версии зависимостей.

### 7.2. Requested и displayed state

При асинхронной сортировке существуют requestedQuery и displayedQuery. Заголовок может показывать pending intent, но строки должны сохранять связь с реально опубликованным displayedQuery.

Пока новый результат не готов, допустимы:

- старое согласованное представление с явным pending status;
- loading-представление нового запроса с placeholders и без старых строк под видом новых;
- частичный результат с явно объявленной completeness.

По умолчанию операции, интерпретирующие видимые позиции, во время несовместимой смены projection временно отклоняются с pending-view reason. Позже можно поддержать выполнение по displayedProjectionRevision с зафиксированными RowId. Нельзя переназначать paste на другие строки после завершения сортировки.

### 7.3. Протокол публикации

1. Взять versioned inputs и их dependency stamp.
2. Подготовить необходимые derived outputs.
3. Проверить, что результат применим к текущему source/query и не перезапишет более новую несовместимую работу.
4. Собрать immutable published view с согласованными данными, projection, layout и interaction.
5. Атомарно заменить указатель на published view.
6. Уведомить подписчиков этого представления.

Коммит данных и публикация могут происходить в одном синхронном проходе для простого grid. Разделение — семантическое, а не требование всегда добавлять microtask, Promise или кадр задержки.

Во время долгого пересчёта старый snapshot должен читать старую совместимую версию данных. Недопустимо оставлять старый порядок строк, но читать значения из уже изменённого mutable store. Возможные реализации: copy-on-write, versioned row records или материализованные immutable окна. Полный persistent store/MVCC не обязателен, но гарантия наблюдаемой неизменяемости обязательна.

Preview, hover и scroll могут публиковаться поверх текущего совместимого displayed data version. Они не ждут всю очередь background compute. Selection, чей target существует только в новой projection, публикуется вместе с этой projection.

В пределах source/query session публикации не возвращаются к более старой уже заменённой версии данных. При batching допустимо публиковать завершённую согласованную партию, даже если canonical state уже принял следующую, с явным признаком отставания. Это отличается от принятия ответа отменённого query: provenance и порядок сохраняются, а backlog остаётся ограниченным.

### 7.4. Подписки и стоимость

- getSnapshot возвращает кэшированную ссылку до следующей релевантной публикации.
- Неизменённые rows, columns и geometry blocks переиспользуются.
- Есть подписки на slices/селекторы с определённой equality semantics.
- Все выбранные slices читаются из одной атомарно установленной публикации.
- Внешний callback не видит промежуточную сборку snapshot.

React-адаптер строится вокруг контракта external store; Vue-адаптер не создаёт глубокую реактивную копию всего row store. Публичные read-only snapshots не требуют deep-clone всей таблицы.

## 8. Projection и вычисления

### 8.1. Сначала корректный pipeline

Первая реализация использует небольшой явный pipeline с объявленными зависимостями. Пример для локального аналитического набора:

source → row computations → filter → grouping → aggregation → group ordering → flattening.

Это пример, а не универсальный порядок. Leaf sorting, сортировка групп по агрегату, pagination, pivot и вычисления по видимому порядку требуют отдельных стадий и семантики.

До реализации каждой стадии определить: входы, выходы, completeness requirements, стабильность порядка, обработку ошибок и влияние на identity.

Пользовательское подключение произвольного порядка стадий в первом публичном API не требуется. Поддерживаемые композиции должны быть перечислены и проверены.

### 8.2. Инкрементальная обработка

```ts
type Invalidation =
  | { kind: 'none' }
  | { kind: 'incremental'; change: StageDelta }
  | { kind: 'rebuild'; reason: string };
```

Каждая оптимизированная стадия сохраняет полный корректный rebuild path. Scheduler выбирает incremental или rebuild с учётом масштаба изменений и измеренной стоимости. Инкрементальность не обещает O(1): обновление одной строки может сдвинуть множество позиций или затронуть глобальную формулу.

DAG вводится там, где есть реальные зависимости, например между вычисляемыми колонками. Flat grid без формул и групп не должен создавать универсальный граф задач на каждую ячейку.

### 8.3. Формулы и агрегаты

Разделить:

- row-local expressions, не зависящие от положения строки;
- cross-row formulas с явными адресами и зависимостями;
- group aggregates;
- window/rank/running computations, зависящие от порядка;
- formatted output, который не является вычисляемым значением.

Для формул определить адресацию, поведение при insert/delete/sort, циклы, error propagation и volatile inputs. Вычисление времени и случайности получает явный input/epoch, если нужен deterministic replay. Не исполнять пользовательские формулы через произвольный eval.

Возможность aggregation.remove должна объявляться отдельно: sum/count обычно допускают дешёвую корректировку, а min/max при удалении текущего экстремума требуют дополнительной структуры или пересчёта группы. Floating-point суммы могут отличаться из-за порядка вычислений; точность и критерий сравнения должны соответствовать типу данных.

### 8.4. Исполнители и scheduling

Compute contract должен допускать main-thread executor и позднее worker executor. Задача несёт dependency stamp, cancellation signal и приоритет; результат несёт stamp и проверяется перед публикацией.

Worker использует сериализуемый план или заранее зарегистрированные операторы. Произвольный comparator closure из приложения нельзя автоматически перенести в worker или на сервер.

Приоритеты: direct input и editor feedback, viewport, необходимые вычисления для публикации, background prefetch. Длинные задачи кооперативно уступают поток. Для потоковых данных нужны bounded queues и политика перегрузки, иначе отмена каждого пересчёта новым update может навсегда остановить публикации.

Latest-wins допустим для устаревшего запроса. Для непрерывного потока данных использовать bounded batching и ограниченный срок жизни партии: закончить согласованный batch, затем обработать следующий.

## 9. DataSource и удалённая обработка

### 9.1. Source, query session и result window

Не сводить все модели к getRows(start, end). Offset- и cursor-источники имеют разные гарантии. Общая абстракция описывает capabilities и session; конкретный access mode задаётся discriminated union.

QuerySession связана с QueryKey, QueryGeneration, SourceEpoch и, если сервер предоставляет, consistency token. Она владеет запросами, блоками кэша, полнотой и count metadata.

```ts
type CountInfo =
  | { kind: 'exact'; value: number }
  | { kind: 'estimate'; value: number }
  | { kind: 'unknown' };

type ReadRequest =
  | { kind: 'range'; start: number; endExclusive: number }
  | { kind: 'cursor'; after?: string; before?: string; limit: number };
```

Cursor source не обещает произвольный jump-to-row, если не предоставляет механизм позиционирования. UI должен знать это ограничение. Count относится к конкретному запросу, а не ко всему source независимо от фильтров.

### 9.2. Capability contract

| Область | Что описывается |
| --- | --- |
| Access | Local, range или cursor; возможность resolve-by-ID и позиционирования |
| Query | Поддерживаемые filter operators, sort fields, grouping/aggregation и их ограничения |
| Semantics | Null ordering, collation, timezone и типы либо идентификатор согласованного профиля семантики |
| Consistency | Snapshot token, stable ordering, sequence/version guarantees или явное отсутствие таких гарантий |
| Mutation | Read-only, atomic batch или per-item; optimistic concurrency; idempotency |
| Streaming | Порядок событий, обнаружение пропусков, resume/resync |
| Selection/export | Выполнение по query predicate или только по явно доступным RowId |

Неподдерживаемый запрос возвращает структурированный reason. Planner не должен угадывать семантику неизвестного сервера.

### 9.3. Partial data

Локальный filter/sort/aggregate над удалённым подмножеством разрешён только для явно ограниченной области или при доказанной полноте соответствующей области. Например, полностью загруженная группа может иметь свои допустимые локальные операции, но это не делает весь dataset полным.

Комбинированный план обязан сохранять порядок операций. Фильтрация после server pagination не эквивалентна фильтрации до неё. Агрегат по загруженным строкам помечается partial и не используется как глобальный итог без разрешённой семантики.

### 9.4. Загрузка и устаревшие ответы

Отдельно моделировать idle, loading, ready, error, cancelled, end-of-data и отсутствие конкретной записи. HTTP error или сетевой сбой не превращается в пустой успешный диапазон.

Каждый ответ проверяется по session identity/generation и request identity. AbortSignal сокращает лишнюю работу, но не гарантирует, что ответ не придёт. Поздний ответ старого query не изменяет новый кэш, count или selection.

Кэш имеет бюджет и eviction policy; учитывается не только число строк, но и размер payload/производных структур. Отдельно определяется, что происходит с черновиком редактирования при вытеснении строки: pin entry, хранение draft по ID или явная отмена.

### 9.5. Потоковые события

Source event содержит epoch, sequence/version и typed patch. При обнаруженном пропуске выполняется resync по контракту source. Если source не предоставляет ordering/consistency guarantees, grid не выдумывает их и документирует eventual consistency.

Coalescing разрешён для замен одного значения, когда промежуточные значения не нужны семантике. Нельзя молча выбрасывать increments, insert/delete ordering, записи аудита или события, от которых зависит подтверждение операции.

Snapshot и live stream должны иметь согласованную точку подключения, если требуется отсутствие пропусков. Без server watermark/resume token это не гарантируется одним клиентским scheduler.

## 10. Selection, focus и взаимодействия

### 10.1. Разные понятия выбора

Не объединять в один неявный массив:

- выбор записей по RowId;
- прямоугольные диапазоны ячеек в конкретной projection;
- logical active cell и keyboard anchor;
- выбор всех результатов удалённого запроса;
- визуальное выделение группы.

Для row selection поддержать explicit IDs и, при наличии capability, query selection с исключениями. Query selection связывается с запросом и явно определяет, является ли это набором на snapshot token или динамическим правилом для будущих совпадений. При изменении фильтра политика — сохранить привязку к старому query, сбросить либо запросить явное преобразование; молчаливое переосмысление запрещено.

### 10.2. Диапазоны ячеек

Для первого релиза рекомендуется простая политика:

- диапазон строится в отображаемом порядке и несёт ProjectionRevision;
- при начале paste/fill фиксируются логические цели и порядок колонок;
- изменение сортировки или фильтра во время активного жеста отменяет жест с понятной причиной;
- после смены projection обычный row selection сохраняется по ID;
- cell range сбрасывается до сохранившейся active cell или очищается, если она исчезла;
- сохранение точного набора ячеек через смену projection добавляется как отдельная опция с собственным контрактом.

Эти defaults можно изменить в ADR, но они должны быть едиными для всех адаптеров и покрываться тестами. Нельзя хранить только две границы и считать, что они однозначно определяют прежний набор выбранных записей после сортировки.

### 10.3. Interaction state machines

Семантика жеста хранится в core: idle, selecting, editing, filling, resizing и необходимые вложенные состояния. На уровне конфликтующих жестов действует один active interaction owner.

Платформа переводит pointer/keyboard/input events в нормализованные сообщения. Pointer capture, document listeners и browser focus остаются в DOM-слое. Core определяет start/update/commit/cancel и причины отказа.

Обязательные пути завершения: pointer cancel, Escape, потеря capture, удаление целевой строки, source reset, unmount/dispose. Нельзя зависеть только от pointerup.

Resize preview и drag preview могут объединяться по кадрам. Итоговый resize commit фиксирует ширину один раз в соответствии с выбранной history policy. Scroll не проходит через Undo.

### 10.4. Editing

Editor session содержит RowId, ColumnId, исходную версию значения, draft, состояние validation и причину завершения. При live update той же ячейки draft не перезаписывается молча.

Для начальной политики: сохранить draft и сообщить конфликт при попытке commit, предложив приложению explicit overwrite/reload/rebase. Last-write-wins допустим только как выбранная политика, а не скрытый default.

IME composition имеет отдельный lifecycle: Enter во время композиции не завершает редактирование. Keyboard semantics определяет core с учётом нормализованного isComposing, а наблюдение browser composition events — задача адаптера.

### 10.5. Logical focus

Core хранит logical focus по идентичности. DOM adapter обеспечивает фактический focus после появления нужного элемента и подтверждает, что он соответствует актуальной публикации.

При виртуализации использовать выбранную и проверенную стратегию: roving tabindex либо aria-activedescendant. При отсутствии целевой ячейки в DOM должна быть корректная промежуточная стратегия на контейнере. Focus не должен случайно попадать в переиспользованный элемент другой строки.

При удалении active row fallback определяется детерминированно: ближайший доступный узел в новом отображаемом порядке или контейнер при пустом наборе. При скрытии active column выбирается доступная колонка по явному правилу.

## 11. История, optimistic writes и конфликты

### 11.1. Undo — отдельная возможность

History хранит доменные изменения, логические цели и предусловия обратной операции. Она не является журналом всего runtime state.

Одна логическая операция paste/fill обычно создаёт один history entry. Серия вводов в editor может объединяться по session ID. Scroll, hover и measurements туда не входят. История query/layout включается отдельной политикой, чтобы Undo редактирования не превращался неожиданно в отмену прокрутки или фильтра.

Нужны ограничения по числу записей и объёму сохранённых значений. Массовый импорт должен заранее объявлять, поддерживается ли Undo и каков его лимит. Повторный Undo не должен удерживать неограниченное число полных snapshots.

### 11.2. Конфликты

Обратный patch применяется только при совместимых текущих значениях/версиях. Внешнее обновление ячейки после пользовательской правки делает слепое восстановление опасным.

В первом релизе разумен строгий default: вернуть history-conflict, не менять данные. Более поздние политики могут поддержать rebase, разрешённое field-level undo или compensating remote mutation.

Source reset инвалидирует несовместимые history entries. Изменение ID/incarnation и схемы проверяется при Undo/Redo.

### 11.3. Серверная запись

Локальный optimistic commit и remote confirmation — разные этапы. Для сохранения требуются mutation ID и, если сервер поддерживает, expected row versions и idempotency key.

Atomic local paste не означает atomic server paste. Если источник поддерживает только per-item writes, API явно возвращает частичный результат либо отклоняет операцию, которая требует all-or-nothing. Клиентский rollback не отменяет уже записанные сервером строки.

При отказе optimistic patch удаляется/компенсируется с учётом более новых локальных операций. Нельзя восстанавливать весь старый snapshot и тем самым затереть последующие изменения.

Сетевой timeout после отправки записи может означать неизвестный результат, а не доказанный отказ. Повтор записи допустим по idempotency contract; иначе требуется reconciliation/read-back или решение приложения.

Порядок acknowledgements может отличаться от порядка запросов. Engine сопоставляет их по mutation ID и версии, а не по времени получения ответа.

## 12. Geometry, viewport и virtualization

### 12.1. Разделение модели и измерения

Core вычисляет логическую геометрию из размеров и порядка узлов. DOM layer измеряет доступные элементы и передаёт результаты как входы с NodeId, ColumnId при необходимости, layout key и measurement generation.

Layout key учитывает факторы высоты: ширины колонок, шрифт/тема, wrapping и версию влияющего на размер содержимого. Старое измерение от переиспользованного DOM-элемента не применяется к новой строке.

Для переменных высот выбрать структуру с приемлемой стоимостью prefix sums, поиска позиции и update, например Fenwick tree или блочную структуру. Выбор определяется профилем insert/delete/reorder; конкретная структура не является публичным контрактом.

### 12.2. Scroll anchoring

Anchor хранит NodeId и смещение внутри узла, а не только scrollTop. После измерения или вставки строк engine восстанавливает относительное положение anchor, если он существует.

При удалении anchor действует определённый fallback. При пользовательском scroll/jump-to-row предыдущая компенсация не должна бороться с новым намерением. Native browser anchoring и собственная компенсация настраиваются совместно, чтобы не применить коррекцию дважды.

### 12.3. Окна и overscan

Render window ограничивается viewport и overscan. При большой таблице виртуализируются обе оси, если это соответствует поддерживаемым feature combinations.

Overscan имеет предел и может учитывать скорость прокрутки. Алгоритм не должен раздувать DOM без ограничений. ResizeObserver feedback обрабатывается пакетно и с защитой от циклов, а не произвольными синхронными DOM-read/DOM-write на каждую ячейку.

Для очень больших виртуальных размеров отдельно проверить пределы scroll container в целевых браузерах. Если требуются segmented/rebased scrolling, вводить их по реальному сценарию и тесту, не обещать бесконечную координатную область браузера.

### 12.4. Pinning и grouped headers

У layout есть логические start/center/end regions с поддержкой RTL. Одна логическая ячейка не превращается в несколько независимых editable или focusable сущностей из-за pinned rendering.

Группа колонок может разбиваться на визуальные сегменты по regions. Layout выдаёт каждому сегменту стабильный ID, границы, clipping и правила размещения подписи. Логический group ID остаётся общим.

Перемещение подписи группового заголовка при горизонтальной прокрутке вычисляется относительно видимой части её сегмента. Подпись удерживается в доступной области и ограничивается границами группы; она не следует за scroll бесконечно. Политика центрирования/прилипания и измерение ширины подписи задаются отдельно. При ширине подписи больше доступного участка включается clipping/ellipsis.

Pinned regions, scroll anchoring и group header placement используют один layout model. Разрозненные поправки координат в Vue-компонентах не допускаются.

## 13. Render contract и адаптеры

Render contract содержит ровно информацию для отображения и взаимодействия с опубликованным состоянием:

```ts
interface PublishedGridView {
  readonly publicationId: PublicationId;
  readonly stamp: PublicationStamp;
  readonly displayedQuery: QueryDescriptor;
  readonly status: PresentationStatus;
  readonly window: RenderWindow;
  readonly layout: LayoutSnapshot;
  readonly interaction: InteractionSnapshot;
  readonly accessibility: AccessibilitySnapshot;
}
```

RenderWindow содержит видимые узлы и колонки либо version-bound read handles. Handle не может читать случайное latest state. Произвольный getter, замкнутый на mutable row store, не обеспечивает snapshot consistency.

Renderer может хранить DOM refs, состояние монтирования editor и платформенные измерения. Он не выполняет заново filter/sort/group и не принимает независимые решения о selection semantics.

Core не обязан создавать объект для каждой ячейки при каждой публикации. Разрешены shared blocks, lazy reads в пределах закреплённой версии и compact typed buffers. Эти оптимизации скрыты за контрактом.

Vue-адаптер реализует coarse-grained refs или селективную реактивность вокруг immutable snapshots. React-адаптер предоставляет стабильные subscribe/getSnapshot и соответствует useSyncExternalStore. Нельзя выставлять один постоянно мутируемый объект snapshot и ожидать, что React заметит внутренние изменения.

В первом production UI используется DOM. Canvas renderer — отдельная возможность после доказанного ограничения DOM и собственного плана accessibility/editing. Архитектурная независимость renderer не требует строить Canvas заранее.

SSR не обязателен для каждого продукта. Core должен импортироваться без window/document. Если адаптер объявляет SSR/hydration, он обеспечивает согласованное начальное состояние, стабильные IDs и отсутствие browser-only reads на сервере. Иначе режим явно обозначается client-only.

## 14. Accessibility и работа с платформой

Accessibility включается в модель с первого интерактивного вертикального сценария.

Нужно определить:

- role grid/treegrid/table в зависимости от поведения;
- логические row/column indexes и counts, включая header rows;
- неизвестный total count и частичную загрузку;
- semantics selection, expanded state, sorting, readonly/editable и validation errors;
- keyboard navigation между клетками и внутри editor;
- вход/выход из grid через Tab;
- focus при удалении, фильтрации, pinning, виртуализации и закрытии editor;
- объявления loading, ошибок и результатов операций без потока повторяющихся сообщений.

AccessibilitySnapshot передаёт логические сведения; DOM adapter отображает их в HTML/ARIA. Виртуализация и pinning не должны создавать дублирующиеся доступные ячейки или неверные индексы.

Автоматические проверки дополняются ручными сценариями screen reader и keyboard-only. Минимум — одна согласованная поддерживаемая комбинация Windows/browser/screen reader и одна macOS/browser/VoiceOver, если обе платформы входят в продуктовую поддержку. Целевую матрицу закрепить в репозитории.

Платформенные порты покрывают clipboard read/write, измерения, focus, scheduling и при необходимости download/export. Clipboard и другие browser permissions обрабатываются адаптером; core получает данные или структурированную ошибку.

## 15. Публичный API

### 15.1. Основные операции

```ts
const grid = createGrid({
  source: localRows(data, { getRowId: row => row.id }),
  columns,
  features: [selection(), editing(), sorting()],
});

const receipt = grid.execute({
  type: 'cells.set',
  cells: [{ rowId: 'r-42', columnId: 'price', value: 120 }],
  atomicity: 'local',
});

const snapshot = grid.getSnapshot();
const unsubscribe = grid.subscribe(onPublishedChange);

unsubscribe();
grid.dispose();
```

Этот пример показывает пользовательскую форму API. Импорт-пути и точный вывод типов фиксируются после проверки bundle graph и type tests.

### 15.2. Стабильная поверхность

Основной API включает create, execute, read snapshot, subscribe и dispose. Для удобства допустимы типизированные фасады grid.sorting.set или grid.editing.commit, если они вызывают тот же command path.

Не публиковать изменяемые state objects, внутренние task queues и методы обхода validation. Advanced entrypoints существуют только для реального extension contract, а не как способ добраться до каждой функции реализации.

Команды типизированы discriminated unions. Отсутствующая feature даёт unsupported-capability, а не silent no-op. Статическое ограничение API по набору features полезно, но не должно делать TypeScript diagnostics нечитабельными; runtime-проверки всё равно нужны.

Для подписок можно добавить selectSnapshot(selector, equality) или subscribeSelector. Сначала зафиксировать требования к стабильности ссылок и согласованности; конкретную библиотеку сигналов выбирать по измерениям и совместимости адаптеров.

### 15.3. Восстановление состояния

PersistedGridState отделяется от runtime snapshot. Он содержит версионированные пользовательские настройки: ширины/порядок/видимость колонок, фильтры, sorting и при необходимости layout preferences.

Не сериализовать DOM refs, transient gestures, task handles, весь cache и pending mutations как обычные настройки. Сохранение draft/offline writes — отдельный протокол.

Restore проверяет версию схемы и наличие ColumnId, возвращает список применённых и пропущенных настроек. Миграции persisted state нужны до первой стабильной публикации API v2.

### 15.4. Ошибки

Структурированные коды: validation-failed, unsupported-capability, stale-target, ownership-conflict, history-conflict, source-error, write-outcome-unknown, computation-failed, cancelled, disposed. Message предназначен человеку; код и details — приложению.

Ошибка пользовательской команды не скрывается только в console.error. Неожиданная внутренняя ошибка имеет trace ID и диагностическую запись, но не раскрывает исходные значения ячеек по умолчанию.

## 16. Features, plugins и пакеты

Feature declaration описывает ID, contract version, зависимости, команды, query/compute contributions, state slice при необходимости и dispose.

Engine проверяет несовместимые feature combinations и конфликты ID при создании. Порядок registration не должен незаметно менять semantics. На старте динамическое добавление/удаление features во время работы не поддерживается: это отдельная сложная миграция состояния.

Плагины не мутируют canonical state напрямую. Они готовят commands/patch plans, объявляют derived computations или читают публичный контекст. Перед commit их результат проверяется.

Tree-shaking подтверждается production build fixtures. Массив features сам по себе не гарантирует исключение тяжёлой зависимости. В зависимости от фактического графа импортов допустимы root exports или документированные subpath exports.

Рекомендуемые физические границы:

| Пакет/область | Содержимое | Когда выделять |
| --- | --- | --- |
| datagrid-core | Контракты, координатор, state, data, базовые interaction и viewport | Основной пакет |
| datagrid-vue | Адаптер и Vue-компоненты согласно существующей модели продукта | Сразу для текущего UI |
| datagrid-react | React-адаптер и UI bindings | Когда поддерживается React; небольшой prototype раньше для проверки границ |
| datagrid-testing | Reference pipeline, fixtures, source simulators, harness | При реальном переиспользовании тестовых средств |
| formula/pivot modules | Тяжёлые опциональные зависимости | Subpath или отдельный пакет по bundle/lifecycle требованиям |
| shared DOM/platform | Измерения, browser ports, общие жесты | Внутренний модуль; пакет только при самостоятельной пользе |

Внутри core разумны директории contracts, engine, state, data, compute, interaction, viewport, publication и diagnostics. Конкретное перемещение файлов выполняется после определения владельцев и зависимостей, а не как первый шаг миграции.

Если текущий orchestration package используется несколькими продуктами Affino, его сохраняют. В grid-specific core переносятся только семантические правила grid; общие DOM/lifecycle механизмы не нужно дублировать.

## 17. Диагностика, производительность и lifecycle

### 17.1. Наблюдаемость

Предусмотреть диагностический интерфейс с ограниченным ring buffer и режимом отключения. Для операции видны operation ID, причина invalidation, выбранный execution path, продолжительность стадий, число затронутых строк и PublicationId.

Полезные события: command accepted/rejected, transaction committed, query started/cancelled/discarded, stage rebuilt/incremental, publication ready, source gap, history conflict и cache eviction.

Инструмент explain рассказывает, почему операция невозможна или почему произошёл полный пересчёт. Диагностика должна помогать разбирать реальное поведение, а не только печатать длительность функции.

### 17.2. Производительность

Бюджеты задаются как измеримые стартовые цели, а не обещания для любого hardware и любых custom renderers.

| Метрика | Что измерять |
| --- | --- |
| Input-to-presentation | От keyboard/pointer input до отображённого результата |
| Commit duration | Синхронная критическая секция локальной фиксации |
| Compute duration | Время pipeline и отдельных стадий, incremental/rebuild отдельно |
| Scroll quality | Пропущенные кадры, blank frames, ошибка anchor, main-thread work |
| Publish lag | От входящего data update до согласованной публикации |
| Memory | Пиковая память, размер кэша/history, retained data после dispose |
| Bundle | Минимальный grid и отдельно grouping/pivot/formula/adapter fixtures |

Для фиксированного эталонного устройства можно начать с P95 keyboard-to-visible ≤32 ms и локальной критической секции small edit ≤4 ms. Это инженерные гипотезы для калибровки: измерять отдельно подготовку, вычисления и paint, не скрывая задержку до commit.

16,7 ms при 60 Hz и 8,3 ms при 120 Hz — интервалы полного кадра, включающие browser work. Их нельзя целиком выделить JavaScript grid. Для скролла отслеживать пропущенные кадры и распределение времени работы, а не только средний FPS.

Первичная матрица: маленький flat grid; 100 тыс. локальных строк с ограниченным видимым окном; широкая таблица с горизонтальной виртуализацией; grouping/aggregates; динамические высоты; remote source с неизвестным count; поток обновлений одновременно с editing. Числа колонок, размер payload, частота updates, браузер, hardware и build фиксируются для каждого benchmark.

CI gates устанавливаются после baseline, учитывают шум и повторные прогоны. Регрессия должна быть воспроизводимой. Один удачный microbenchmark не доказывает качество взаимодействия.

### 17.3. Lifecycle

dispose идемпотентен: снимает подписки/listeners, отменяет запросы и задачи, завершает operation handles, освобождает observers и ссылки на DOM. Поздние callbacks после dispose не меняют состояние.

Сброс source создаёт новый epoch, отменяет несовместимые операции и определённо очищает cache/history/selection согласно политике. Экспортированному snapshot нельзя тайно изменить данные ради освобождения памяти; потребитель, удерживающий старый snapshot, удерживает и соответствующую память. API и документация должны объяснять срок жизни таких ссылок.

## 18. Проверки корректности и качества

### 18.1. Эталонная модель

Нужен простой reference pipeline с полным пересчётом. Он проверяет результат оптимизированной реализации на одинаковых данных и конфигурации. Reference должен иметь независимо проверенную семантику; копия production-алгоритма не является сильным oracle.

Для чисел/decimal/comparators определить точность и tie-break rules. Для равных ключей сортировки использовать документированный устойчивый порядок: исходный order token или дополнительный стабильный ключ. В remote pagination tie-break обеспечивает серверный query contract.

### 18.2. State-machine и property-based testing

Генерировать последовательности edit, insert, delete, sort, filter, group, select, undo, redo, resize и source update. После каждого наблюдаемого шага проверять инварианты, а не только отсутствие исключения.

Обязательные свойства:

- локальная failed transaction оставляет прежнее authoritative state;
- incremental output совпадает с reference output;
- старый snapshot не изменился после следующей операции;
- каждый published node и cell читаются из совместимой версии;
- stale response не изменяет новый query;
- история не перезаписывает конфликтующие внешние обновления;
- selection/focus разрешаются в допустимые узлы либо имеют явный fallback;
- dispose завершает ресурсы и pending outcomes.

### 18.3. Управляемая асинхронность

Fake source и test scheduler позволяют переставлять ответы, задерживать validation, имитировать отказ, partial success, sequence gap и неизвестный исход записи. Тесты не зависят от случайных sleep.

Replay record содержит начальное состояние, конфигурацию, команды и внешние входы. Пользовательские payload не сохраняются в production trace без явного включения; для воспроизводимых fixtures используются обезличенные данные.

### 18.4. Browser, types и packaging

- Browser tests: реальный keyboard/pointer/IME lifecycle, фокус, виртуализация, pinned regions, resize и measurements.
- Accessibility: автоматическая проверка плюс ручной keyboard/screen-reader checklist.
- Type tests: inference для columns/commands, unsupported feature combinations и extension types.
- Package tests: exports, отсутствие framework imports в core, tree-shaking и SSR import safety, если заявлена.
- Lifecycle tests: повторные mount/unmount, переключение source, освобождение observers и прекращение callbacks.

Не тестировать каждую внутреннюю функцию ради количества тестов. Приоритет — границы контрактов, race conditions и пользовательские сценарии, которые могут незаметно повредить данные.

## 19. Решения, которые нужно зафиксировать до расширения реализации

Нужен небольшой набор ADR, каждый с решением, альтернативами, причиной и проверяемыми последствиями.

| ADR | Обязательное решение | Начальный default |
| --- | --- | --- |
| 01. Ownership | Кто владеет каждым slice и как подтверждается controlled update | Internal + ограниченные controlled slices; без hot-switch ownership |
| 02. Identity/value | ID, версии записей, null/missing/error, comparator semantics | Стабильные RowId/ColumnId; отдельные projection NodeId |
| 03. Command lifecycle | Commit/publication/confirmation, cancellation и reentrancy | Короткий локальный commit, queued reentrancy, явные outcomes |
| 04. Publication | Совместимость версий, old view во время pending, immutable reads | Сохранение предыдущего view; атомарный swap publication |
| 05. Source/query | Range/cursor, completeness, consistency и write guarantees | Запрет неявной локальной глобальной обработки partial data |
| 06. Selection/editing | Range при sort/filter, logical focus, conflict policy | Отмена активного жеста; range до active cell; отказ при конфликте записи |
| 07. History | Что отменяется, лимиты, реакция на external update | Только поддерживаемые domain edits; строгая проверка конфликтов |
| 08. Pipeline | Поддерживаемые стадии, формулы, ties, fallback | Полный reference path и постепенная incremental оптимизация |
| 09. Rendering/a11y | DOM contract, focus strategy, измерения и pinning | DOM renderer; общая logical модель и платформенные измерения |
| 10. API/package | Stable surface, feature registration, persisted state | Компактный API; статический feature set; измеренный tree-shaking |

Начальный default — предложение для Affino, а не универсальное правило отрасли. Его можно изменить по реальному продуктовому требованию, но нельзя оставлять соответствующую семантику неявной.

Не требуется писать все ADR до первой строки кода. ADR 01–04 и минимальная локальная часть 06 нужны для первого вертикального сценария; остальные завершаются перед соответствующим этапом. Прототип может проверять решение, но не должен незаметно стать стабильным контрактом.

## 20. Поэтапная миграция

### Этап 0. Карта текущей системы и baseline

Работа:

- прочитать текущие contracts, public exports и ключевые сценарии;
- перечислить владельцев данных, selection, editing, query и layout;
- найти прямые mutations и пересечения core/Vue/orchestration;
- составить dependency map и матрицу реально поддерживаемых features;
- сохранить минимальные reproductions известных проблем;
- измерить существующие performance/bundle/memory baselines.

Результат: короткая карта «что оставить, что обернуть, что перенести, что удалить» и несколько нарушенных либо пока непроверенных инвариантов. Предполагаемая проблема не объявляется доказанной без ссылки на код или воспроизведения.

Критерий выхода: можно проследить один edit от DOM до source и обратно до render, назвать владельцев и места публикации. Никакого массового переименования пакетов на этом этапе.

### Этап 1. Первый вертикальный сценарий

Минимальный сценарий: локальные строки со стабильными ID, две-три колонки, редактирование значения, сортировка по этой колонке, logical focus и простое Undo.

Работа:

- реализовать command handler и локальный transaction boundary;
- отделить canonical commit от published view;
- сделать version-bound чтение опубликованных данных;
- подключить текущий Vue UI через новый adapter boundary;
- использовать простой полный pipeline;
- перенести eligibility и commit/cancel семантику этого сценария в core;
- сразу проверить keyboard и базовую accessibility.

Критерий выхода: edit перемещает строку после сортировки; focus остаётся связан с той же записью; renderer ни разу не получает новые значения в несовместимом старом представлении; Undo возвращает значение при отсутствии конфликта.

Это первый работающий Engine 2.0. Для него не нужны grouping, общий DAG, worker, remote source и полный plugin framework.

### Этап 2. Внешнее владение и конфликты

Работа:

- добавить controlled query/selection по выбранному контракту;
- ввести внешний source update, row versions и SourceEpoch;
- отделить editor draft от подтверждённого значения;
- добавить delayed validation и проверку read set;
- определить terminal outcomes и dispose;
- проверить Undo после external update.

Критерий выхода: внешняя правка не теряется при позднем editor commit; запрос controlled update не считается подтверждением; source reset не принимает старые ответы; pending операции завершаются предсказуемо.

### Этап 3. Полные локальные interactions и layout

Работа:

- перенести range selection, paste/fill и editing state machines;
- определить атомарную validation массовой операции;
- реализовать transient resize/drag path;
- согласовать row/column virtualization, pinning и measurement identity;
- реализовать scroll anchoring и grouped header segments;
- добавить memory/history limits.

Критерий выхода: paste с ошибкой в одной ячейке не меняет другие при atomicity='local'; sort/filter во время жеста обрабатываются выбранной политикой; measurement старого DOM-элемента не меняет новую строку; keyboard focus сохраняется при виртуализации.

### Этап 4. Удалённый source и optimistic writes

Работа:

- реализовать один конкретный remote access mode, необходимый продукту;
- ввести query sessions, completeness, count metadata и stale-result rejection;
- добавить fake source с управляемым порядком ответов;
- реализовать source capabilities и ограничения UI;
- при необходимости добавить optimistic writes с mutation IDs и acknowledgements;
- определить query selection и partial failure policy.

Критерий выхода: два запроса с обратным порядком ответов дают последний актуальный результат; неизвестная длина не считается нулём; sort/filter над partial data не выдаются за глобальные; remote partial success и unknown write outcome не маскируются под atomic success.

Cursor и range не обязательно реализуются одновременно. Неподдерживаемый access mode явно отклоняется.

### Этап 5. Производные возможности и оптимизация

Работа:

- последовательно переносить grouping, aggregates, formula и pivot по продуктовому приоритету;
- для каждой стадии сначала иметь корректный reference/rebuild path;
- ввести точечную invalidation и сравнение incremental/reference;
- добавить batching потоковых обновлений;
- проверить selectors, structural sharing и стоимость публикации;
- вводить worker только для подтверждённого bottleneck с учётом transfer/copy overhead.

Критерий выхода: оптимизация сохраняет семантику и даёт измеримое улучшение на целевом сценарии; небольшая flat-таблица не получает лишнюю обязательную стоимость тяжёлых features.

### Этап 6. Проверка независимости адаптеров и API

Работа:

- создать небольшой React-адаптер или интеграционный prototype с edit/sort/select;
- доказать, что UI не воспроизводит скрытую семантику Vue;
- зафиксировать stable public API, feature contracts и persisted-state schema;
- проверить production bundles и exports;
- написать migration guide со старых API;
- удалить прямые bypass-пути после перевода потребителей.

Критерий выхода: один набор core semantics tests применим ко всем адаптерам; минимальный React-сценарий корректно работает со snapshot identity; consumers не обращаются к внутренним mutable stores.

Полный React product UI нужен только при продуктовой необходимости. Небольшой второй адаптер полезен раньше как проверка архитектурных границ.

### Этап 7. Release gates

Это финальная проверка, а не начало тестирования.

- Прогнать feature/scenario matrix и fault injection.
- Проверить поддерживаемые keyboard/screen-reader сценарии.
- Сравнить performance, memory и bundles с согласованными budget/baseline.
- Проверить source changes, re-mount/dispose и долгую сессию.
- Подтвердить документацию ограничений и migration guide.

Критерий выхода: каждая заявленная возможность имеет определённую семантику, поддерживаемые сочетания и проверку. Неподдерживаемые возможности возвращают явный отказ. Название Engine 2.0 не является основанием заявлять все потенциальные функции документа реализованными.

### Правила переходного периода

Миграция проводится по вертикальным сценариям. На каждый переведённый slice существует один владелец: старый путь либо новый. Facade/compatibility adapter может сохранять прежний API, но не создаёт вторую независимо изменяемую копию состояния.

Для проверки вычислений допустим shadow mode: старый и новый pipeline получают одинаковые входы, новый только сравнивает результат. Shadow pipeline не отправляет network writes, callbacks пользователя и history events второй раз.

Feature flag переключает целый поддерживаемый сценарий с понятной rollback boundary. Не смешивать по случайному условию старую selection policy и новый transaction writer.

Breaking API допускается. Но изменение semantics selection, null ordering или Undo должно быть описано как поведенческое изменение, а не только как переименование метода.

## 21. Обязательные приёмочные сценарии

| Сценарий | Ожидаемое поведение |
| --- | --- |
| Edit sort key | Значение и новое положение строки публикуются согласованно; focus связан с RowId |
| Paste с одной invalid cell | При atomicity='local' нет ни одного изменения; возвращены ошибки validation |
| Paste и смена sorting | Цели фиксированы или операция отменена по политике; значения не попадают в другие записи |
| Async validation и external update | Перед commit выявлен конфликт релевантной версии |
| Remote queries A, затем B; ответ B приходит первым | Поздний A не заменяет данные, count и cache session B |
| Remote count неизвестен | UI показывает неопределённую длину; источник не считается пустым |
| Select all remote results | Хранится query-bound правило/исключения; не требуется загружать все строки |
| Undo после server update той же ячейки | Строгий default возвращает history-conflict, не затирая обновление |
| Remote write timeout | Возвращён unknown outcome; нет слепого повторного неидемпотентного запроса |
| Remote partial write success | Есть поэлементный результат; не заявляется atomic confirmation |
| Измерение после переиспользования DOM | Старое measurement отвергнуто по identity/generation |
| Строки добавлены выше viewport | Anchor остаётся на той же записи с совместимым offset |
| Удалена active row | Focus переходит по документированному fallback |
| IME composition и Enter | Composition не принимается за завершение editor session |
| Pinning + grouped headers + горизонтальный scroll | Геометрия едина; подпись ограничена своим сегментом; нет дублирования logical focus |
| Ошибка формулы или plugin stage | Контролируемая ошибка; нет частичной публикации и повреждённого authoritative state |
| Непрерывный data stream | Очередь ограничена; публикации продолжаются; сохраняются необходимые delta semantics |
| Dispose при активных запросах | Все handles завершены; поздние callbacks не меняют engine |
| Старый snapshot после новой публикации | Значения старого snapshot остались прежними |
| Controlled state отказался принять update | Engine не выдаёт предложение за подтверждённое изменение |

Для compute failure после успешного canonical commit default следующий: commit остаётся действительным, предыдущий согласованный view сохраняется со статусом error/stale, published outcome операции завершается failed. Автоматический откат данных не выполняется. Восстановление — исправление конфигурации/данных, retry или явная компенсирующая команда. Это правило исключает ложное утверждение, что ошибка renderer или derived stage отменила уже подтверждённые данные.

Не все ошибки обязаны блокировать всю публикацию: error value конкретной формулы может быть обычным согласованным результатом ячейки. Нужно различать доменную ошибку значения и отказ стадии построить корректную projection.

## 22. Что реализовать первым, а что отложить

| Сразу | После работающего вертикального сценария | Только по подтверждённой необходимости |
| --- | --- | --- |
| Ownership и identity | Remote query sessions | Canvas renderer |
| Typed command outcomes | Advanced grouping/pivot | WASM/Rust core |
| Atomic local commit | Incremental dependency tracking | Универсальный query optimizer |
| Publication protocol | Полные range/fill сценарии | Collaborative editing и CRDT |
| Immutable/version-bound reads | Optimistic remote mutations | Полный event sourcing |
| Logical focus и keyboard semantics | Worker executor для тяжёлых стадий | Динамическая выгрузка plugins |
| Reference pipeline | Дополнительные adapters | Распределённые транзакции |
| Контрактные тесты и baseline | Полные performance gates по feature matrix | Неограниченный plugin pipeline |

Не откладывать решения о completeness, controlled ownership и remote confirmation до появления второго адаптера или первого production сервера. Полную реализацию можно отложить; контракт должен заранее оставлять корректный путь.

## 23. Конкретное первое задание на реализацию

Цель первой инженерной итерации — доказать фундамент на одном полном сценарии, сохранив полезные существующие реализации Affino.

Последовательность:

1. Исследовать текущий edit/sort/select/render path и перечислить владельцев состояния со ссылками на код.
2. Зафиксировать ADR 01–04 и минимальную interaction policy.
3. Составить минимальные типы RowId, ColumnId, CellRef, ChangeSet, CommandReceipt, OperationHandle и PublishedGridView.
4. Реализовать один command cells.set с parsing/validation и атомарным локальным commit.
5. Построить простой sorted projection из versioned inputs.
6. Опубликовать immutable view и перевести один существующий Vue-сценарий на него.
7. Сохранить logical focus по RowId и поддержать Undo без конфликтов.
8. Добавить внешний update той же ячейки и строгую проверку конфликта.
9. Проверить отсутствие mutations старого snapshot, отсутствие лишних уведомлений при неизменившемся selected slice и корректный dispose.
10. Сравнить с baseline; описать оставшиеся ограничения и выбрать следующий вертикальный сценарий.

Не начинать с массового перемещения файлов, написания всех row models или миграции всех composables. Первый результат должен быть запускаемым и проверяемым пользователем.

Definition of Done первой итерации:

- есть работающий edit → sorted projection → publish → focus → Undo;
- commit/publication/confirmation не смешаны в один success flag;
- core принимает логические команды и не зависит от Vue/DOM;
- редактор и engine не владеют двумя независимыми подтверждёнными значениями;
- renderer получает согласованную публикацию;
- конфликт с внешним update не приводит к потере данных;
- проверки привязаны к инвариантам, а не к внутреннему устройству методов;
- нет неподтверждённых обещаний о performance и полном покрытии Engine 2.0.

## 24. Основания и актуальные ориентиры

Архитектурные defaults этого документа являются предлагаемыми решениями для Affino. Они не выдаются за обязательный отраслевой стандарт. Официальная документация ниже подтверждает отдельные ограничения интеграции и практические сценарии; она не предписывает внутреннее устройство Engine 2.0.

1. [React — useSyncExternalStore](https://react.dev/reference/react/useSyncExternalStore). Кэшированная идентичность и неизменяемость snapshots; контракт подписки; server snapshot при SSR. Основание для разделов 7 и 13.
2. [TanStack Table — Table State](https://tanstack.com/table/latest/docs/framework/react/guide/table-state). Внешнее управление состоянием и его отдельными частями. Ориентир для ownership и API.
3. [AG Grid — Server-Side Filtering](https://www.ag-grid.com/javascript-data-grid/server-side-model-filtering/). Передача filter model источнику и выполнение фильтрации на сервере. Ориентир для remote query semantics.
4. [AG Grid — Server-Side Row Selection](https://www.ag-grid.com/javascript-data-grid/server-side-model-selection/). Различие серверного selection state и списка загруженных выбранных строк. Ориентир для query selection.
5. [AG Grid — High Frequency Updates](https://www.ag-grid.com/javascript-data-grid/data-update-high-frequency/). Пакетная обработка частых обновлений. Ориентир для scheduling; конкретные интервалы AG Grid не переносятся в Affino автоматически.
6. [TanStack Virtual — Virtualizer](https://tanstack.com/virtual/latest/docs/api/virtualizer). Контракты ключей, измерений и виртуализации. Ориентир для viewport implementation.
7. [W3C WAI-ARIA APG — Grid and Table Properties](https://www.w3.org/WAI/ARIA/apg/practices/grid-and-table-properties/). Логические counts и indexes, когда DOM содержит часть таблицы. Основание для accessibility contract.

Эти источники проверялись при разборе исходной концепции в этой сессии 18 октября 2026 года. При реализации конкретного адаптера версии зависимостей фиксируются отдельно и проверяются по соответствующей документации.
